Notes for Kimi-K2.6

  • Weights: moonshotai/Kimi-K2.6 (revision 7eb5002f) stores the routed experts in INT4 (compressed-tensors, group 32) and the other weights in BF16. The recipes train a BF16 copy, written by miles' tools/convert_kimi_int4_to_bf16.py at commit ee36bb2a (the launcher's prepare step), which dequantizes the experts; the script at 78527b91 differs only in leaving quantization_config in the output config.json. miles loads the copy through Megatron-Bridge (--megatron-to-hf-mode bridge --model-name kimi_k25) with no torch_dist conversion, so --hf-checkpoint and --ref-load are both its directory.
  • MODEL_ARGS come from miles' scripts/models/kimi-k25.py at commit 78527b91, printed by miles/utils/external_utils/model_args_utils.py kimi-k25; run the command from a miles checkout at that commit, in the radixark/miles v0.1.0 image, whose Megatron-Bridge (commit 7f0fb345) holds the Kimi K2.5 bridge. miles has no K2.6 model file: its K2.5 launcher and model page cover both models, and K2.6's config.json differs from K2.5's (revision 4d01dfe0) only in eos_token_id.
  • It trains on its own rows, built with --loss-mask-type kimi_k25 --trust-remote-code (data/README.md).
  • The bridge builds the whole vision-language model, so the first pipeline stage also holds the vision tower and its projector (0.47B parameters), which text rows never reach.
  • The checkpoint's modeling_deepseek.py imports is_torch_fx_available, which transformers 5 removed. Megatron-Bridge at 7f0fb345 restores it (conversion/transformers_compat.py) before it loads that file, which fails to import outside the bridge under transformers 5.12.1.
  • 3 of the campaign's 23 runs stopped at actor initialization with an ImportError or AttributeError in the checkpoint's tokenizer code, loaded from the Hugging Face modules cache (~/.cache/huggingface/modules) that the ranks of a node write at the same time; the one relaunched unchanged ran through.

#1attune-tp8-pp16-ep16353.4 tokens/s/GPUTP8 PP16 EP16 DP2PP 16, no recompute, expandable segments off
  • Starting point: miles' Kimi launcher, scripts/run_kimi_k25.py with scripts/models/kimi-k25.py at miles 0.1.0 (model page https://miles.radixark.com/docs/models/kimi/kimi-k2.5, "Kimi K2.5 / K2.6"). miles publishes it as a GRPO recipe validated on 32 nodes of 8 H200 that trains the INT4 checkpoint with fake quantization and Adam on the CPU, with no tokens/s figure. Ported to this workload in BF16 with its layout (TP 8 with sequence parallel, PP 8, CP 4, EP 32, full recompute) and Adam on the GPU on 256 H200, it measured 149.6 tokens/s/GPU (149.8 in an earlier run of the same configuration); ATTUNE tuned it to 353.4 (+136%). A 23-step run of this recipe, profiled on its last step, measured 354.6 over steps 5-19.
  • Each pipeline stage spans two nodes (TP 8 x DP 2), and EP 16 spreads each MoE layer's experts over those 16 GPUs. With 16 stages each GPU holds 2 to 4 of the 61 layers, which leaves the memory to drop both recompute and context parallelism; the ranks the measured run's log shows use up to 117 GB of 140 before the end-of-step cache release.
  • With PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True, as in the reference run, a tuning run of this layout measured 216.3 tokens/s/GPU. miles empties the CUDA cache after every step (clear_memory in miles/utils/memory_utils.py), so the allocator takes its memory from the driver again each step.
